# 供给侧定价与分成标准

> 参考:OpenRouter(直通官方价 + 充值手续费)、RapidAPI(佣金抽成)、国内中转站(平台统一倍率)。
> 目标:消除"成本价由供给方自报"带来的作弊/套利空间,把**消费者定价、调度选型、平台盈利**三者解耦。

## 三条标准(必读)

### 标准 1:消费者价 = 平台统一价,不随渠道浮动

消费者通过标准 OpenAI 兼容 API 消费时,统一按 **`ModelRatio`(全局零售倍率)** 计费。

- `ModelRatio` 由平台全局维护,锚定官方公开价(见 `relay/billing/ratio/model.go` 内注释)。
- **任何渠道(含供给方托管渠道)不得影响消费者价格。** 供给方渠道不设独立零售价;消费者看到的价格与渠道无关。
- 现状对照:✅ 已满足——`postConsumeQuota` 用全局 `ModelRatio` 计费,`EffectiveCost` 仅用于成本记账与调度,不参与消费者计费。

### 标准 2:成本价锚定官方基准,供给方不得自由定价

`cost_ratio`(成本倍率)用于**平台与供给方内部结算**及**成本最优调度**,由以下约束管住:

1. **下限**:`cost_ratio >= 1.0`——供给方声称的成本不得低于官方零售基准(`ModelRatio`)。设置低于 1.0 视为**无效/恶意低报**,提交时拒绝。(现状:下限 0.01,过松,收紧到 1.0。)
2. **上限**:`cost_ratio <= 3.0`——供给方声称的成本不得高于官方零售基准的 3 倍,防虚报抬高结算。可配置 `MAX_COST_RATIO` 覆盖。
3. **官方锚定说明**:`ModelRatio` 即"官方零售基准";`cost_ratio=1.0` 表示成本等于官方价,`>1.0` 表示上游有溢价(如官方 key 之外的路由/代理)。
4. **平台可覆盖**:管理员可对单个渠道的 `cost_ratio`/`model_cost_ratio` 强制修正(`IsShared` 渠道留痕)。
5. **触发条件收紧**:只有 `supplier_allowed_channel_types` 白名单内、且通过 `testChannel` 预校验的渠道才能接入(现状已满足)。

> 为什么是"≥1.0":供给方托管的是官方 Key(或等价上游),成本不可能低于官方零售价——这正是防止"供给方报 0.01 抢调度量"的关键。

### 标准 3:平台盈利与调度解耦

- **调度选型**:按 `EffectiveCost` 选成本最低渠道(零售价统一 → 成本最低 = 供给方收益最低 = 平台利润最高)。此逻辑保留。
- **平台盈利**:平台收益来自 **分成 + 流水**,**不依赖"压渠道成本"**:
  - 分成:`platform_ratio`(默认 20%)按公式 `利润 = 零售 − 成本` 抽取(现状已实现)。
  - 说明:当成本被锚定在 `[1.0, 3.0]` 后,平台不会为了高利润而偏爱低报渠道——因为低报已被标准 2 拒绝。
- **套利防线**(标准 3 的延伸):
  - 供给方既是供给者又是消费者时,其消费按**统一零售价**计费,分成照算——供给方没有套利空间。
  - 调度排除"消费者 token 与渠道 owner 同属一人"的路径(`CacheGetRandomSatisfiedChannel` 的 `excludeOwnerId`);代理转发路径(`/v1/oneapi/proxy/:channelid`)仅限管理员,防指定渠道绕过。

## 实现说明

四个相互配合的机制(对应代码):

1. **可信成本申报**:供给方提交 Key 时 `cost_ratio` 锚定官方价校验(`controller/supplier.go`),落 `cost_decl_status` 待审;管理员经 `/api/cost-decl/` 审批核准/驳回,可顺带指定信任等级。
2. **信任阶梯(爬坡闭环)**:渠道 `trust_level`(1-5)参与调度——路由改为**加权随机**(`model/cache.go weightedPick`),`score = 1/(成本×信任惩罚)`。低信任渠道选中概率低但非零(保证爬坡);成本记账仍用纯成本 `EffectiveCost`,不被信任污染。
   - **自动爬坡**:新渠道信任 1 起步,连续 `settlementTrustUpgradeAfter`(=7)个周期**对账正常**则自动 +1,封顶 5(`model/settlement.go upgradeChannelTrust`)。靠真实运营自动获得更高调度权重,不再只等管理员手动提。
   - **异常自动降**:连续 `settlementTrustDegradeAfter`(=2)个异常周期降 1 级,最低 1,只降不升(`degradeChannelTrust`)。管理员仍可在成本申报审批时手动封顶/干预。
3. **套利防线**:`CacheGetRandomSatisfiedChannel` 接收 `excludeOwnerId`,供给方不能消费自己托管的渠道。
4. **对账**:结算时用 `used_quota` 周期增量对账(`settlements.used_quota_end` 快照),偏差超阈值判异常,异常单等待管理员"核验入账",同时作为信任升降的依据。

## 成本竞价的固有风险与对策

`cost_ratio` 是供给方**自报**的成本倍率,平台用 `[1.0, MAX_COST_RATIO]`(默认上限 3.0)约束。这套"自报 + 区间锁死"的机制在对抗恶意报价上有**三个固有风险**,需要正视并持续加固:

### 风险 1:虚报抬高(吃平台利润)

成本倍率可报到上限 3.0。同一模型,真实成本 1.0 的供给方报 3.0,结算时按 `成本 + 利润×20%` 分成,供给方多拿的部分就是平台少赚的利润。**信任等级越高的渠道越敢报**(反正流量大),平台利润被"虚报成本"悄悄榨走。

**对策**:
- 成本申报需管理员人工核准(`cost_decl_status`),不是提交即生效。
- 信任惩罚让低信任渠道就算报价高也分不到量;配合**对账降权**,异常渠道被压制。
- **推荐加固**:把固定上限改为**动态锚定**(`官方价 × 动态系数`),报价与锚的偏离度进入调度权重,偏离越大越不可信;或对申报成本做**账单抽查审计**,虚报一次降权 + 限制申报。

### 风险 2:低价恶意抢量

成本报 1.0(贴下限)用低价抢走流量,但真实成本其实更高——通过**降质**(低配模型冒充、限流、缓存命中)压低真实成本。调度只看 `cost_ratio`,分不清"真便宜"和"假便宜"。

**对策**:
- 成本下限锁死 1.0,报更低(<1.0)被拒,防止"免费/倒贴抢量"。
- 信任爬坡 + 对账降权形成负反馈:一旦降质导致对账异常,信任被降,抢到的量反而被收走。
- **推荐加固**:引入**服务质量指标**(成功率、响应时长、内容质量抽检)进入调度权重,不只靠成本。

### 风险 3:没有价格发现机制

`[1.0, 3.0]` 是固定区间,不随市场供需变化。真实市场里上游降价了,平台的成本锚仍停在旧值,成本失真——平台既不能及时吃到降价红利,也可能把已经降价的模型按旧成本结算给供给方。

**对策**:
- 平台定期同步官方公开价(`relay/billing/ratio/model.go`)作为锚,`cost_ratio` 是**相对锚的倍率**而非绝对价,锚更新即全局生效。
- **推荐加固**:让调度权重反映"报价 vs 市场价"的偏差,而非只看绝对倍率;或对报价偏离市场过大的渠道走人工审批。

> **结论**:当前机制是"**自报成本 + 区间锁死 + 信任负反馈**"的保守方案——能挡住大部分恶意报价,但不是市场竞价。真正的价格发现(实时锚定、动态区间、服务质量加权)是后续演进方向,详见 [FEASIBILITY.md](FEASIBILITY.md) 与 [ARCHITECTURE.md](ARCHITECTURE.md)。
