# Neo Matrix 项目可行性评估

> 基于 3 轮代码审计 + 竞品/合规调研,评估项目能否安全、可落地地运营。结论:**技术上可行,但当前形态不可直接生产运营**,需先修复 P0/P1 资金与安全问题,并明确合规边界。

## 一、竞品格局

| 类型 | 代表 | 特点 | 与 neo-matrix 关系 |
|---|---|---|---|
| 生态派 | 阿里云/火山/百度智能云 | 聚合是生态延伸,非独立生意 | 竞品,定位不同(企业向) |
| 聚合派 | 硅基流动/非线智能/ThinkFlow | 最接近 OpenRouter,覆盖国产+开源模型,合规路线 | **最像的竞品** |
| 海外中转派 | B.AI/EasyRouter | 解决 GPT/Claude 便捷调用,"官转"5-8 折 / 灰色倒卖 | **neo-matrix 的差异化空间,但合规风险最高** |

**OpenRouter 商业模式(为什么难复制)**:靠充值手续费 5-5.5%(不做加价),靠调度/稳定性/开发场景绑定构建壁垒。国内不可复制:合规(境外未备案模型无路径)、信任(模型掉包侵蚀)、上游断供(不掌握上游核心资产)。

**neo-matrix 的差异化**:个人闲置 Key 托管分成。市场没有成熟先例,是"中心化中转(A 形态)+ 个人微供应商入驻"的新组合。

## 二、合规风险(已决策:走海外中转高风险路线)

国内中转站 6 类风险直接适用:
1. 非法经营罪(无证提供电信增值服务)
2. 侵犯公民个人信息罪(对话记录转卖,50 条即入罪)
3. 数据跨境传输违规
4. 协助规避准入限制
5. 虚报计费与模型掉包
6. 数据泄露连带责任

**四条红线(即使高风险路线也绝不能碰)**:不转卖数据 / 不虚报计费 / 不模型掉包 / 不协助规避准入。已写入平台规则(见 `docs/rules/RULES.md` 10.5)。

## 三、技术风险(代码审计结论)

### P0(必须修才能上线)—— 已在本轮修复 ✅
| 问题 | 修复 |
|---|---|
| 提现并发透支 | ✅ 原子扣减 |
| 成本申报状态可伪造 + ModelCostRatio 无校验 | ✅ 白名单绑定 + 区间校验 |
| SSRF(供给方任意 BaseURL) | ✅ BaseURL 白名单 + 私有 IP 校验 + 供给方人工审核 |
| proxy 免费通道 | ✅ 仅限管理员 |
| 前端构建产物未提交,全新 clone 启动 panic | ✅ README 明确先构建前端 |
| tiktoken 启动联网崩溃 | ✅ 降级到近似计费 |

### P1(高危)—— 已修复大部分 ✅
| 问题 | 修复 |
|---|---|
| 审核并发双重入账/退款 | ✅ 状态原子翻转 |
| admin 读 root access_token 提权 | ✅ Omit + omitempty |
| quota 扣减成负数 | ✅ 条件更新 |
| 结算入账错误被吞 | ✅ 事务化 |
| ClientIP 伪造绕过限流 | ✅ SetTrustedProxies(nil) |
| CORS 全开 + 会话无 SameSite | ✅ 收紧 + SameSite=Lax |
| SESSION_SECRET 随机 / goroutine 无 recover / 无 graceful shutdown | ✅ 修复 |

### P2/P3(上线后优化,本期未做)
- 图片/音频不记 cost_quota,结算对文本不公
- 重叠结算周期可重复入账
- 日志无轮转 / SQLite 连接池过大
- 密码重置明文回传 / 无 body 限制 / 验证码内存 10 条
- 结算窗口漂移间隙

## 四、推广策略建议

1. **供给方冷启动**:个人闲置 Key 变现是卖点,先从小圈子(开发者社区/Telegram 群)邀约少量供给方试用,积累真实结算数据。
2. **信任建设**:透明定价表 + 可查结算单 + 明确的对账异常处理,是对抗"中转站跑路"疑虑的关键。
3. **差异化定位**:主打"成本最优调度 + 个人分成",避免与巨头拼价格。
4. **合规降险**:实名供给方、留存知情同意、不碰数据转卖,降低刑事风险敞口。

## 五、上手难度评估

| 项 | 评估 |
|---|---|
| 5 分钟跑起来 | ⚠️ 需要先构建前端(已改 README 明确);离线需 TIKTOKEN_CACHE_DIR |
| 生产部署 | 单机 SQLite 简单;高可用需 MySQL/Redis/多机(本期未验证) |
| 运维排查 | 日志按天落盘 + request-id,可 grep;但无轮转/无监控埋点 |
| 文档 | 业务向齐全(ARCHITECTURE/SUPPLIER_PRICING/RULES);运维向已补 DEPLOYMENT |

## 六、结论

- **能否运作**:技术上可行(全链路已验证);商业上依赖"供给方有足够闲置 Key"的双边冷启动。
- **最大风险**:合规(海外中转) > 跑路信任危机 > 上游封号 > 代码漏洞。
- **下一步建议**:
  1. 先跑一轮真实小流量验证结算/提现闭环;
  2. 上线前完成 P2 关键项(图片 cost_quota、结算窗口);
  3. 明确供给方实名与合规红线落地。
